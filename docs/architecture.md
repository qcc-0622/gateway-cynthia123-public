## 项目定位

Chat Gateway 是一个部署在云服务器上的 **AI API 中转网关**，位于客户端（如 RikkaHub / 橘瓣）和各 AI 服务商之间。

**它解决的核心问题：**

| 痛点 | 网关方案 |
|------|---------|
| 想用多家 AI 服务商，每家接口格式不同 | 统一入口 + 自动协议转换 |
| 长对话 token 越来越贵 | BP2 滚动摘要压缩历史 |
| 重复内容反复计费 | 四断点缓存策略（BP1/BP3/BP4） |
| AI 聊久了"失忆" | 语义记忆召回（Ombre Brain） |
| 新开对话不知道之前聊了什么 | 跨会话摘要继承 + 无缝上下文注入 |
| 没有统一的用量/花费统计 | 自动归档 + 成本核算 |

## 多上游管理

### 设计思路

网关不绑定任何单一 AI 服务商。所有上游（provider）以 JSON 配置文件管理，可通过 Admin UI 动态增删，无需重启。

### 上游数据模型

```python
@dataclass
class Upstream:
    name: str               # 上游名称（唯一标识）
    base_url: str           # API 地址
    api_key: str            # 主 API Key
    api_format: str         # "anthropic" 或 "openai"
    is_active: bool         # 是否启用
    cached_models: list     # 该上游可用的模型列表
    extra_keys: list        # Token 分组（见下文）
    cache_ttl: str          # 默认缓存 TTL: "1h" / "5m" / "off"
    force_think: bool       # 是否强制注入思考模式
```

### Token 分组（extra_keys）

一个上游可以配置多个 API Key，按用途和模型分流：

```json
{
  "key": "sk-xxx",
  "label": "gemini-专用",
  "purpose": "summary",        // "chat" | "summary" | "all"
  "models": ["gemini-3-flash"],  // 精确匹配
  "model_prefixes": ["[G-"],    // 前缀匹配
  "cache_ttl": "5m"             // 可覆盖上游默认 TTL
}
```

**路由优先级**：精确模型匹配 > 前缀匹配 > 用途匹配 > 主 Key 兜底。

### 模型路由流程

```
客户端请求: model = "55a3::[A3-按量]claude-opus-4-6"
                      ↓
解析 "upstream::model" 格式 → 指定上游 55a3 + 模型名
                      ↓
在 55a3 的 cached_models 中确认模型存在
                      ↓
选择最匹配的 API Key（按 extra_keys 规则）
                      ↓
确定 cache_ttl（Key 级覆盖 > 上游默认）
```

如果客户端没有指定上游前缀，网关会遍历所有活跃上游的 `primary_cached_models`，找到第一个匹配的。

## 协议转换矩阵

AI 行业目前有两套主流 API 格式：

| | Anthropic 格式 | OpenAI 格式 |
|--|---------------|------------|
| 端点 | `/v1/messages` | `/v1/chat/completions` |
| 消息结构 | `content: [{type, text}]` 数组 | `content: "string"` 或数组 |
| 系统提示 | 独立 `system` 字段 | `role: "system"` 消息 |
| 流式事件 | `message_start/content_block_delta` | `chat.completion.chunk` |

**网关支持全部 4 种组合，自动完成转换：**

| 客户端 → 上游 | 处理方式 |
|--------------|---------|
| Anthropic → Anthropic | 直传（仅做预处理） |
| Anthropic → OpenAI | `anthropic_to_openai()` 转换请求 + 流式事件反向翻译 |
| OpenAI → Anthropic | `openai_to_anthropic()` 转换请求 + 流式事件反向翻译 |
| OpenAI → OpenAI | 直传（仅做预处理） |

**转换覆盖范围：**
- 请求体结构（消息格式、参数名映射）
- 流式 SSE 事件（逐 chunk 实时翻译）
- 非流式响应体
- thinking/reasoning 块处理

这意味着客户端只需要实现一种格式，就能无感访问所有上游——无论上游用的是哪种 API。

## 预处理管线

这是网关最核心的部分。每条请求在转发给上游之前，要经过一条 **26 步预处理管线**（Anthropic 路径完整版），按功能分为 5 大阶段：

### 阶段 1：身份识别

| 步骤 | 做什么 | 为什么 |
|------|--------|--------|
| 计算 fingerprint | 对消息序列做哈希，生成会话指纹 `fp_xxxx` | 标识这是"哪个对话"，用于 BP2 摘要和归档 |
| 计算 history_hash | 对除最后一条外的消息做哈希 | 检测"重新生成"（re-roll）：如果 hash 相同说明用户只是重新生成了最后一条 |
| 检测 tag | 从系统提示词中提取频道标签 | 区分日常/工作/技术等不同场景 |

### 阶段 2：消息清洗

| 步骤 | 做什么 | 为什么 |
|------|--------|--------|
| 去除客户端 cache_control | 清掉客户端自带的缓存标记 | 网关统一管理缓存策略，避免冲突 |
| 标准化 thinking 块 | 统一 `reasoning_effort` 格式 | 不同上游对 thinking 参数的支持不一致 |
| 去除历史 thinking | 删掉历史消息中的思考块 | 避免签名校验失败 + 省 token |
| 去除空 text 块 | 删掉 `text: ""` 或缺少 text 字段的内容块 | 上游会因此返回 400 |
| 反伪造校验 | 去除用户消息中伪造的网关元数据 | 安全：防止用户注入假的系统指令 |
| 清理孤儿消息 | 删掉缺少对应 tool_use 的 tool_result | 上游要求 tool_use/tool_result 成对出现 |

### 阶段 3：上下文增强

| 步骤 | 做什么 | 为什么 |
|------|--------|--------|
| 无缝上下文注入 | 新对话自动注入最近的对话记录 + 摘要 | 开新窗口不会"失忆" |
| **BP2 滚动摘要** | 把旧对话压缩为摘要（详见下节） | 省 token、控制上下文长度 |
| **语义记忆召回** | 检测新话题 → 从 Ombre Brain 搜索相关记忆 | AI 能"想起"之前聊过的事 |

### 阶段 4：缓存优化

| 步骤 | 做什么 | 为什么 |
|------|--------|--------|
| 添加 BP1 标记 | 在系统提示词末尾插入 `cache_control` | 系统提示词几乎不变，缓存命中率最高 |
| 添加 BP3 标记 | 在冻结窗口末尾插入 `cache_control` | 较早的对话不会变，适合缓存 |
| 添加 BP4 标记 | 在最后一条 AI 回复插入 `cache_control: 5m` | 滑动窗口，每轮刷新 |
| 强制 ≤4 槽位 | 如果超过 4 个缓存标记，按优先级裁剪 | Anthropic 硬件限制最多 4 个缓存断点 |

### 阶段 5：最终注入

| 步骤 | 做什么 | 为什么 |
|------|--------|--------|
| 追加时间提醒 | 在最后一条用户消息末尾加上当前时间 | AI 需要知道"现在几点"来给出合理回复 |
| force_think 注入 | 追加 `{"role": "assistant", "content": "<think>\n"}` | 强制 AI 先思考再回答（如果上游配置了） |

> **OpenAI 路径**是精简版：只做身份识别 + 消息清洗 + 最终注入，不含 BP2/记忆/缓存注入（因为 OpenAI 格式不支持 cache_control）。

## BP2 滚动摘要系统

### 问题

AI 按 token 计费。一段 100 轮的对话可能包含 10 万+ token，每次发消息都要把完整历史发送一遍——越聊越贵。

### 方案

当对话超过 **32 轮**（可配置），网关自动把前面的旧对话压缩成一段 **滚动摘要**，替换进消息序列。

```
压缩前（80 轮对话）:
  [消息1] [消息2] ... [消息60] [消息61] ... [消息80]
  ←————— 这些太旧了 ————→ ←—— 最近 20 轮 ——→

压缩后:
  [BP2摘要: "之前聊了XXX..."] [消息61] ... [消息80]
  ←— 一段话概括 60 轮 ——→  ←—— 保留完整 ——→
```

### 四种工作模式

| 场景 | 处理方式 |
|------|---------|
| **冷启动**（新对话，无摘要） | 查找 48h 内其他会话的摘要，跨会话继承 |
| **完美匹配**（摘要覆盖的消息数 = 目标位置） | 直接使用，零延迟 |
| **滚动更新**（有旧摘要，但新增了几轮） | 用旧摘要 + 新消息拼接；后台异步生成新摘要 |
| **需要重建**（积压太多新轮次） | 本轮用旧摘要，后台启动重建任务 |

### 关键设计

- **异步重建**：摘要生成不阻塞当前请求，用 `asyncio.create_task` 在后台完成
- **锁机制**：同一会话的多个并发请求不会触发重复重建
- **自动继承**：新开对话可以自动继承最近会话的摘要，实现"无缝衔接"
- **手动编辑**：支持通过 Admin UI 手动修改摘要内容

## 四断点缓存策略

### 背景

Anthropic API 支持 **Prompt Caching**：对请求中标记了 `cache_control` 的部分，服务端会缓存已计算的 KV-cache，下次命中时大幅降低延迟和成本。但有限制：**最多 4 个缓存断点**。

### 断点布局

```
System Prompt [━━━━━━━ BP1: 1h ━━━━━━━]     ← 几乎不变，命中率 >90%
│
BP2 摘要（如果有的话，内含在 BP3 前缀中）
│
历史消息（冻结窗口）
│ ... 第 N-8 轮 ...
│
第 N-8 轮 AI 回复 [━━ BP3: 1h ━━]            ← 冻结窗口边界，较稳定
│
│ ... 最近 8 轮 ...
│
上一轮 AI 回复 [━━ BP4: 5m ━━]               ← 滑动窗口，每轮刷新
│
当前用户消息 + 时间提醒                        ← 不缓存（每次都变）
```

### TTL 策略

| TTL | 适用场景 | 说明 |
|-----|---------|------|
| `1h` | 支持 Extended Cache 的上游 | 需要 beta header，命中率高 |
| `5m` | 标准 Ephemeral Cache | 不需要 beta，适合所有支持缓存的上游 |
| `off` | 不支持缓存的上游 | 不注入任何 cache_control |

**降级机制**：如果 1h 缓存被上游拒绝（400），自动降级到 5m 重试。

## 语义记忆系统

### 架构

```
Chat Gateway ←→ Ombre Brain（Docker 容器）
                   │
                   ├── 向量数据库（语义搜索）
                   ├── 关键词索引
                   └── 动态记忆桶（random inject）
```

### 写入流程（自动）

每次对话归档时，自动将 `用户消息 + AI 回复` 喂给 Ombre Brain 存储：

```
用户: "今天实验做了 TPC 测试，FF 提升到 82%"
AI: "FF 82% 说明载流子复合得到了有效抑制..."
       ↓
   去重（MD5 哈希）→ 格式化 → Ombre.hold(content, importance=5)
```

### 读取流程（话题触发）

```
用户消息 → bge-m3 向量化 → 与上轮对比余弦相似度
                               ↓
                     < 0.58 → 判定为新话题
                               ↓
              并行: Ombre.breath(query) + 随机采样
                               ↓
                    去重 + 取 Top 5 → 注入到消息中
```

**触发条件**（满足任一）：
- 语义相似度 < 阈值（0.58）→ 话题变了
- 累计 15 轮未触发 → 强制刷新一次

## 数据流向

一条消息从发送到返回的完整生命周期：

```
1. 橘瓣发送请求
   POST https://gateway.example.com/v1/messages
   Body: {model: "55a3::claude-opus-4-6", messages: [...], stream: true}

2. 鉴权
   verify_api_key(request) → 通过

3. 模型路由
   resolve_model_and_upstream("55a3::claude-opus-4-6")
   → upstream=55a3, model="claude-opus-4-6", key="sk-xxx"

4. 预处理（26 步管线）
   → fingerprint=fp_a1b2c3, history_hash=xxx
   → BP2 摘要注入（如果够长）
   → 记忆召回（如果换了话题）
   → 缓存断点注入（BP1/BP3/BP4）
   → 时间提醒追加

5. 协议转换
   客户端=Anthropic, 上游=OpenAI → anthropic_to_openai(body)

6. 转发
   POST https://api.relay-a.example.com/v1/chat/completions (stream=true)

7. 流式返回
   上游 SSE → openai_sse_to_anthropic_sse() → 客户端 SSE

8. 归档（后台）
   → INSERT conversations (tokens_in, tokens_out, cost_usd, ...)
   → feed_pair_to_ombre() (如果启用)
   → 触发 BP2 后台重建（如果需要）
```

## 技术栈

| 层级 | 技术 | 说明 |
|------|------|------|
| 框架 | FastAPI + Uvicorn | 异步 Python Web 框架 |
| 数据库 | SQLite (aiosqlite) | 轻量级，单文件，异步访问 |
| HTTP 客户端 | httpx | 支持流式请求 + 连接池 |
| 向量化 | bge-m3 (SiliconFlow API) | 多语言嵌入模型，用于话题检测 |
| 记忆存储 | Ombre Brain (MCP) | 自建语义记忆容器 |
| 模板引擎 | Jinja2 | Admin UI 渲染 |
| 部署 | systemd + Nginx + Cloudflare | 自动重启 + 反代 + CDN |
| 通知 | PushPlus / ntfy / Web Push | 异常告警 + 余额提醒 |

## 设计原则

| 原则 | 体现 |
|------|------|
| **客户端无感** | 协议转换对客户端透明，只需对接一种格式 |
| **上游可插拔** | JSON 配置 + Admin UI，热添加/切换上游 |
| **成本可控** | BP2 压缩 + 四断点缓存 + 成本追踪三管齐下 |
| **异步不阻塞** | 摘要重建、记忆存储、余额检查全部后台进行 |
| **渐进降级** | 缓存失败自动降级；记忆服务挂了不影响对话 |
| **可观测** | Admin UI 提供仪表盘、日志、成本、摘要全方位监控 |
